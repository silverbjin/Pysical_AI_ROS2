# 13.8. 복합 시뮬레이션 프로젝트 실습 및 검증

## 13.8.1. 도입: 어디까지 동작했는지를 설명하기

앞 절에서는 로봇의 보행, 센서 관측, 팔 조작, 행동 트리(Behavior Tree, BT)를 다루었다. 이제는 여러 구성 요소를 하나의 시스템으로 실행하고, 그 결과를 기록에 근거해 설명할 차례다. 로봇이 목표 근처에 도착했는지, 새로운 관측을 얻었는지, 멈춘 뒤 관련 프로세스까지 종료됐는지는 서로 다른 확인 항목이다.

이 절의 기본 실습은 **이동·관측·상태 확인·안전 종료와 실패 판독**이다. 로봇은 주어진 환경을 이동해 알려진 원통을 관측하고, 대상 부근에 접근해 실제 정착과 새 관측을 확인한 뒤 종료한다. 기본 실습에서는 물체를 집거나 운반하지 않는다.

파지부터 운반·내려놓기까지 연결한 과거 Level 2 실행은 확장 시연 자료로 살펴본다. 최신 버전에서 연속 임무를 안정적으로 재현하는 작업과 Level 3의 파지 이후 동작은 향후 과제로 남긴다. 이를 구분하면 현재 확인된 기능을 배우면서도 아직 검증하지 못한 기능을 완료된 것으로 오해하지 않을 수 있다.

이 절을 마치면 다음을 수행할 수 있어야 한다.

1. 제공된 기본 모드로 복합 시뮬레이션을 실행하고 이동·관측 단계를 확인한다.
2. 진행 표시, 행동 트리 결과, 실제 정착과 종료 기록을 구분한다.
3. 실패했을 때 완료한 단계, 최초 원인, 정지·회수 결과를 설명한다.
4. 과거 시연 기록을 읽고 동작 순서 완료와 전체 평가 통과의 차이를 설명한다.

## 13.8.2. 실습 환경과 실행 범위

### 1. 제공 환경

이 절은 Go2와 Piper를 결합한 MuJoCo 기반 교육용 패키지를 사용한다. 보행은 기존 정책을 유지하고, 관측·접근·행동 트리를 기존 ROS 2 실행 경계로 연결한다. 기준 환경은 Ubuntu 24.04 또는 해당 WSL 환경, ROS 2 Jazzy, MuJoCo 3.13.0이다.

대상은 반경 2cm, 높이 8cm, 질량 20g인 알려진 직립 원통이다. RGB-D 관측에서 이 원통의 표면을 맞추는 방식을 사용하므로, 임의의 콜라 캔이나 일반 물체를 인식하는 시스템으로 해석하지 않는다. 위치 추정도 시뮬레이터의 교육용 기준 위치를 사용한다. 실제 주택의 위치 추정이나 실기 동작을 검증한 환경은 아니다.

|환경|구성|이번 절의 기본 확인 항목|
|---|---|---|
|Level 2: 장애물 환경|박스와 5도 경사로, 테이블 위 원통|이동, 실제 경사 접촉, 대상 관측·접근, 정착, 종료|
|Level 3: 주택 모사 환경|폭 1.1m의 문과 식탁 아래 바닥 원통|문 통과, 대상 관측·접근, 정착, 종료|

Level 번호가 높다고 이번 실습에서 더 많은 조작 단계를 실행하는 것은 아니다. 두 환경 모두 기본 모드의 종료 지점은 이동과 관측을 확인한 뒤다. Level 1과 앞 절의 개별 조작 실습은 기초 기능을 복습할 때 참고한다.

### 2. 기본 모드의 동작 순서

기본 실습의 행동 트리는 다음 순서로 작업을 요청한다.

**시작 대기 → 이동(`navigate`) → 새 관측 확인(`find`) → 종료(`finish`)**

이동 단계에는 지도의 관측 지점으로 이동한 다음, 새 RGB-D 관측을 이용해 대상 부근으로 접근하는 과정이 포함된다. Nav2가 도달 결과를 반환한 뒤에도 로봇의 실제 정착을 확인한다. 관측 단계에서는 이전에 저장한 좌표가 아니라 해당 실행에서 얻은 유효한 원본 관측을 확인한다.

종료 단계에서는 작업을 마치고 소유한 실행 자원을 회수한다. 기본 모드는 MoveIt 계획 서버를 기동하지 않으며 팔·그리퍼의 동작 명령을 발행하지 않는다. 다만 보행과 기본 자세를 유지하는 기존 제어 및 안전 감시는 계속 사용한다.

이 모드는 명령에 `--exercise basic`을 명시해 선택한다. 전체 파지·귀환·놓기 경로인 `full`은 개발자용으로 남아 있다. 이 절의 기본 실습 명령에서 `basic`을 생략하지 않는다.

### 3. 준비와 분리 빌드

소스 다운로드와 OS·ROS 의존성, 원본 자산 및 가상환경의 설치 절차는 제공 자료의 [기본 실습 시작 가이드](START_HERE_13_8_KO.md)를 따른다. 13.5·13.6의 환경 준비를 재사용하되, 소스와 빌드는 13.8용을 사용한다. 외부 모델·정책 자산은 저장소에 모두 포함되어 있지 않으므로 안내된 위치에 별도로 준비해야 한다.

이후 명령은 저장소 루트를 `ROOT`로 설정한 WSL/Linux 터미널에서 실행한다. 아래 가상환경은 앞선 준비 단계에서 생성되어 있어야 한다.

```bash
cd /실제/저장소/경로/Pysical_AI_ROS2_13_8
export ROOT="$PWD"
export CH13_REUSE_BUILD="$HOME/ch13_reuse_13_8_build"
export CH13_REUSE_VENV="$HOME/ch13_reuse_iit_d010212_venv"

bash Ch13/scripts/reuse_13_8/build.sh
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/audit_install.py \
  /tmp/ch13_basic_install_audit.json
```

첫 줄의 경로는 자신의 실제 경로로 바꾼다. 모든 실행 터미널은 같은 build와 venv를 사용해야 한다. 터미널 전체에 venv를 활성화하거나 ROS 패키지 경로를 임의로 앞에 추가하지 않는다. 제공된 `env.sh`가 실행 Python과 필요한 경로를 구성한다.

기존 13.6·13.7 설치 위치를 새 빌드로 덮어쓰지 않는다. 또한 시뮬레이터를 실행하는 동안 빌드, 전체 시험, 대용량 로그 분석을 함께 수행하지 않는다. 개발 시 검증한 기존 환경과 새 OS에서 처음 설치하는 과정은 다르므로, 설치 감사 결과를 확인한 뒤 실습을 시작한다.

## 13.8.3. 기본 실습 실행하기

### 1. 실행 전 소유 상태 확인

먼저 다른 로봇 실행이 남아 있지 않은지 확인한다. 여러 작업 폴더가 같은 로봇 자산을 사용한다면 동일한 실제 공유 잠금 파일을 사용해야 한다.

```bash
cd "$ROOT"
test -e "$ROOT/../ch13_reuse_engine.lock" || \
  touch "$ROOT/../ch13_reuse_engine.lock"

python3 Ch13/scripts/reuse_13_5/inspect_r2_residuals.py \
  /tmp/ch13_before_basic.json
```

`owned_stack_matches`가 빈 목록이고 `engine_lock_free`가 `true`, 결과가 `PASS`인지 확인한다. 다른 실행이 있다면 그 실행을 시작한 터미널에서 정상 종료한다. 잠금 파일의 존재나 오래된 PID만 보고 파일을 삭제하거나 다른 프로세스를 강제로 종료하지 않는다.

### 2. 실행할 소스 고정

실습 결과를 설명하려면 어떤 소스와 설정으로 실행했는지도 알아야 한다. 제공 도구는 소스와 외부 자산의 해시를 기록하고, 일치하는 실행용 복사본을 준비한다. 이 복사본의 준비 자체가 시뮬레이션 성공을 의미하지는 않는다.

```bash
FREEZE="Ch13/dependencies/my_basic_$(date +%Y%m%d_%H%M%S).json"
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/freeze_runtime.py write "$FREEZE"

STAGE="$(mktemp -u /tmp/ch13_basic_stage_XXXXXX.json)"
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/stage_runtime.py \
  --manifest "$FREEZE" --output "$STAGE"

RUN_ROOT="$(python3 -c \
  'import json,sys;print(json.load(open(sys.argv[1]))["runtime_root"])' \
  "$STAGE")"
```

기존 동결 파일을 수정해 현재 소스와 맞추지 않는다. 소스가 달라졌다면 새 이름으로 기록한다. `ROOT`는 자료와 결과를 관리하는 저장소, `RUN_ROOT`는 이번에 실행할 소스 복사본의 경로다.

### 3. Level 2 실행

실행마다 새 UUID를 사용한다. UUID가 달라지면 결과 폴더도 분리되어 이전 실패나 성공 기록을 덮어쓰지 않는다.

```bash
CASE="$(python3 -c 'import uuid;print(uuid.uuid4())')"
EVIDENCE="$ROOT/Ch13/evidence/section_13_8_system/$CASE"
echo "$EVIDENCE"

cd "$RUN_ROOT"
CH13_CAPTURE_OVERLAP=1 CH13_EXPERIMENTAL_SE2=0 CH13_CALLBACK_TIMING=0 \
bash Ch13/scripts/reuse_13_8/env.sh -u \
  Ch13/scripts/reuse_13_8/run_mission.py \
  --repo-root "$RUN_ROOT" \
  --manifest "$RUN_ROOT/$FREEZE" \
  --evidence "$EVIDENCE" \
  --exercise basic --scenario level2_obstacles --auto-start
```

`--auto-start`는 준비 후 `/start_mission`으로 시작 신호를 보낸다. 별도의 engine이나 Nav2 실행을 추가로 시작하지 않는다. 하나의 소유 실행기가 필요한 프로세스를 기동하고 종료까지 관리한다.

### 4. Level 3 실행

Level 2가 종료되고 잔여 프로세스와 잠금 해제를 확인한 뒤 실행한다. 위 명령에서 새 `CASE`와 `EVIDENCE`를 만들고 `--scenario level3_house`로 바꾼다. 소스를 수정하지 않았다면 검증된 같은 `RUN_ROOT`와 `FREEZE`를 사용할 수 있다.

Level 3의 기본 모드도 대상 관측 후 종료한다. 식탁 아래 대상까지 접근했다고 해서 그 위치에서 안전하게 팔을 뻗을 수 있다는 뜻은 아니다. 관측을 위한 접근 가능성과 충돌 없는 팔 경로의 존재는 별도로 검증해야 한다.

## 13.8.4. 상태 확인과 결과 판독

### 1. 진행 표시 읽기

두 번째 터미널에서 실행 터미널이 출력한 `EVIDENCE` 경로를 같은 값으로 설정한 뒤 읽는다.

```bash
cat "$EVIDENCE/live_status.json"
```

`requested`는 요청한 작업, `completed`는 완료한 작업을 나타낸다. 정상적인 기본 모드에서는 `navigate`, `find`, `finish` 순서만 나타나야 한다. `pick`, `return`, `place`가 요청됐다면 기본 모드로 실행했는지부터 확인한다.

진행 파일은 상태 표시용이다. 파일 쓰기가 늦어 마지막 표시가 남아 있을 수 있으므로, 화면의 한 줄만으로 실제 로봇 상태나 최종 결과를 판단하지 않는다. 실행이 끝나면 최종 결과와 종료 기록을 함께 확인한다.

### 2. 최종 결과 읽기

```bash
cd "$ROOT"
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/inspect_case.py --case "$EVIDENCE"

python3 Ch13/scripts/reuse_13_5/inspect_r2_residuals.py \
  /tmp/ch13_after_basic.json
```

기본 실습 결과는 `basic_result.json`에 저장된다. 전체 임무 평가용 `trial.json`과 분리되어 있다. 결과의 범위 표시는 다음처럼 읽는다.

```json
{
  "result": "PASS",
  "scope": "basic_navigation_observation_only",
  "full_mission_success": false
}
```

이 예시는 기본 실습의 이동·관측·종료 검사를 통과했다는 뜻이다. `full_mission_success`가 `false`인 것은 파지·운반·놓기를 평가한 결과가 아니기 때문이다.

기본 결과의 `checks`는 다음 항목을 나누어 확인한다.

|검사|확인하는 내용|
|---|---|
|`motion_observation`, `terminal`|이동·관측·종료 단계와 정상 결과가 확인됐는가|
|`no_manipulation`|파지·귀환·놓기를 요청하거나 조작 기록을 만들지 않았는가|
|`worker`, `goals`|작업 스레드가 종료되고 미회수 goal이나 오류가 없는가|
|`engine`, `children`|정상 종료와 관련 스레드·소유 자식 프로세스 회수가 확인됐는가|
|`recording`, `telemetry`|기본 명령의 기록과 상태 표시 작업이 종료됐는가|
|`world`|해당 환경 통과와 새로운 대상 관측의 근거가 있는가|

Nav2의 도달 결과, 실제 정착, 프로세스 종료는 서로 다른 사건이다. 마지막 잔여 검사에서 소유 프로세스가 없는지와 공유 잠금이 해제됐는지까지 확인한다. 수동으로 중단하려면 실행 터미널에서 Ctrl+C를 한 번 누르고 회수를 기다린다. 취소된 실행이 동작 PASS가 되는 것은 아니며, 정지·회수 결과를 별도로 읽는다.

### 3. 제공 패키지에서 확인한 기본 실습 사례

아래는 동일한 v53 소스로 각 환경을 한 번씩 실행한 결과다. 시간은 시작 신호 이후 기본 결과에 기록된 값이며, sim 시간과 실제 경과 시간을 구분했다.

|환경|기본 결과|sim 시간|실제 경과 시간|최종 접근 오차|
|---|---|---:|---:|---:|
|Level 2|PASS|55.430초|172.921초|10.701mm|
|Level 3|PASS|42.200초|96.307초|32.645mm|

두 사례 모두 이동·관측·종료만 완료했고, 각각 소유 자식 프로세스 11개의 정상 회수와 잠금 해제를 확인했다. 이 값은 특정 실행의 관찰 결과다. 두 환경의 난이도 순위를 결정하거나, 반복 성공률과 실기 성능을 보증하는 값으로 사용하지 않는다. 또한 마지막 열은 대상 부근의 로봇 접근 오차이며, 물체를 내려놓은 위치의 오차가 아니다.

## 13.8.5. 실패를 읽는 순서

실패가 발생하면 먼저 **완료한 단계 → 최초 원인 → 정지·회수 결과**의 순서로 정리한다. 동작 결과가 FAIL이어도 이 세 항목을 근거와 함께 설명하는 것은 실습의 중요한 성과다. 다만 실패를 분석했다는 이유로 이동·관측 결과를 PASS로 바꾸지는 않는다.

|관찰한 현상|먼저 확인할 기록|판독할 때 주의할 점|
|---|---|---|
|이동 요청 후 멈춤|`navigation_summary.json`의 오류·목표·terminal|기한 초과, 안전 중단, 사용자 취소를 구분한다|
|목표 근처에서 이동 완료가 늦어짐|위치·방향 오차와 실제 정착 기록|위치가 가까워진 한 순간만으로 도달을 선언하지 않는다|
|관측 또는 입력 만료|최초 fault와 그때 사용한 원본 관측·수신 시각|마지막 상태의 나이를 최초 위반 시점의 나이로 쓰지 않는다|
|진행 파일이 갱신되지 않음|최종 결과와 `telemetry_delivery.json`|표시 지연과 제어·센서 지연을 같은 원인으로 단정하지 않는다|
|기본 실습에서 팔 관련 기록이 생성됨|실행 인자와 요청 단계|`--exercise basic`인지 확인하고 전체 임무 경로와 구분한다|
|종료했는데 다음 실행이 시작되지 않음|자식 회수와 잔여 검사|오래된 PID나 잠금 파일만 보고 강제 정리하지 않는다|

### 관측의 나이와 메시지 수신 간격

관측이 촬영된 시각, 메시지를 처음 받은 시각, 인식을 마친 시각은 서로 다르다. 시뮬레이션 시간으로 기록한 시각과 프로세스 내부의 monotonic 시각도 직접 빼서 비교하면 안 된다. 같은 시간 기준 안에서 경과를 계산하고, 처리 단계별 기록을 연결해야 한다.

이 패키지는 원본 관측의 300ms 수명과 촬영 시점에 대응하는 TF의 100ms 조건 등을 사용한다. 이는 제공 구현의 권한·안전 계약이다. 모든 ROS 시스템에 적용되는 보편적인 성능 기준으로 받아들이지 않는다. 오래된 관측의 시각을 현재 시각으로 바꾸거나, 과거 좌표를 다시 발행해 새 관측처럼 사용해서는 안 된다.

rosbag의 수신 간격이 벌어졌다는 사실만으로 센서 callback이 같은 시간 동안 멈췄다고 단정할 수도 없다. 기록 프로세스의 지연, 실제 callback의 지연, 원본 촬영 이후 누적 지연을 분리해 살펴본다. 평균 CPU 사용률 하나만으로 특정 스레드의 과부하나 중단 원인이 입증되지는 않는다.

### 실패 사례를 조정 작업으로 바로 연결하지 않기

실패 로그를 읽기 전에 마찰, 힘, 댐핑, 프로세스 우선순위 또는 QoS를 일괄 변경하지 않는다. 어떤 경계에서 무엇이 늦거나 충돌했는지를 먼저 확인해야 한다. 물체를 강제로 고정하거나 충돌 검사를 꺼서 동작을 완성하는 것도 이 실습의 해결 방법이 아니다.

예를 들어 과거 Level 3 전체 임무에서는 식탁과 팔의 충돌이 예상되는 PRE_GRASP 경로가 거절됐다. 이는 계획 검사가 위험한 경로의 실행을 막은 기록이다. 기본 모드가 관측 뒤 종료하는 것과, 전체 임무의 충돌 문제가 해결된 것은 다른 사실이다.

## 13.8.6. 확장 시연: Level 2의 과거 운반·내려놓기

기본 실습을 마친 뒤에는 과거의 연속 임무 기록을 읽는다. 시연 대상은 v28의 `621d134d-be0a-405c-af20-e5ac913940b7` 사례다. 최신 기본 모드에서 이 기록의 동작을 다시 실행하는 실습은 아니다.

```bash
cd "$ROOT"
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/inspect_case.py \
  --case Ch13/evidence/section_13_8_system/621d134d-be0a-405c-af20-e5ac913940b7
```

기록에는 다음 단계가 같은 engine에서 연결되어 있다.

**이동·관측 → 파지·들어올리기 → 물체를 잡고 귀환 → 지지 확인 후 개방 → 물체 분리·팔 후퇴 → 종료**

|관찰 항목|해당 사례의 기록|
|---|---|
|파지 후 최소 상승|101.245mm|
|파지 유지|2.22 sim초, 양 손가락 접촉 100%|
|운반 중 물체의 시작·끝 수평변위|약 3.918m|
|전체 경과|259.912 sim초 / 630.094 wall초|
|로봇 귀환 오차|55.231mm|
|내려놓기 관련 검사|수령 위치·높이·지지·개방·놓은 뒤 유지 확인|

3.918m는 운반 경로를 모두 더한 길이가 아니라, 운반 시작점과 끝점 사이의 물체 수평변위다. 로봇의 귀환 오차와 물체의 수령 위치 오차도 구분해서 읽는다.

이 사례는 BT의 전체 동작 순서를 끝냈지만 최종 임무 판정은 FAIL이었다. 운반 중 물체의 세계 좌표 높이가 23.360mm 낮아져 당시 추가 물리 기준인 20mm를 넘었고, 원래의 시간·로봇 귀환 정밀도 목표도 충족하지 못했다. 세계 높이 하락만으로 물체를 놓쳤다고 해석할 수는 없지만, 정해 둔 검사를 통과했다고 바꾸어 말할 수도 없다.

따라서 이 시연에서 배울 것은 특정 버전에서 전체 동작 순서가 한 번 실행됐다는 사실과, 그 기록을 항목별로 평가하는 방법이다. 최신 코드의 안정적인 연속 실행이나 반복 성공률은 이 사례만으로 입증되지 않는다. 자세한 판정과 보존 위치는 [Level 2 확장 시연 해설](DEMO_13_8_LEVEL2_ARCHIVE_KO.md)을 참고한다.

## 13.8.7. 필요한 로그만 남기고 오프라인으로 분석하기

기본 실행기는 필요한 토픽을 선택해 rosbag를 기록한다. 별도의 기록 명령을 무조건 추가하기보다, 먼저 해당 실행의 `bag_closed`와 bag의 종료 정보를 확인한다. 모든 토픽과 원본 영상을 장시간 기록하면 저장 공간과 기록 부하가 불필요하게 커질 수 있다.

보존할 자료는 다음 세 묶음으로 생각하면 편리하다.

|자료|목적|
|---|---|
|작은 결과·요약|기본 결과, 완료 단계, 오류, 종료 상태를 빠르게 확인|
|소스·설정 식별 자료|실행한 버전, 설정, 외부 자산의 일치를 확인|
|필요한 원본 기록·압축본|관측·접촉·시간 흐름을 상세 분석하고 실패를 재구성|

새로 실행한 기록의 bag를 점검하려면 종료 후 다음 도구를 사용한다. 출력 파일명은 기존 결과와 겹치지 않게 정한다.

```bash
cd "$ROOT"
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/inspect_recording.py \
  --bag "$EVIDENCE/bag" --output /tmp/ch13_my_recording_check.json
```

선택한 센서·BT 기록의 재생 수신을 확인하려면, 실제 실행이 모두 종료됐고 분석용 ROS domain 136이 다른 작업에 사용되지 않는 상태에서 다음 도구를 사용한다.

```bash
bash Ch13/scripts/reuse_13_8/env.sh \
  Ch13/scripts/reuse_13_8/replay_recording.py \
  --bag "$EVIDENCE/bag" --output /tmp/ch13_my_offline_replay.json
```

이 도구는 분석용 domain에서 선택한 기록을 수신하며 engine이나 controller를 시작하지 않는다. 재생 결과가 PASS여도 원래 임무가 성공한 것은 아니며, 오래된 관측에 새로운 제어 권한이 생기는 것도 아니다. 실시간 제어의 QoS나 실행 설정을 바꾸는 명령으로 사용하지 않는다.

저장소를 내려받았다고 과거의 모든 대형 bag와 raw archive가 함께 제공되는 것은 아니다. 필요한 압축 보존본과 manifest를 확보한 경우에만 새 폴더로 복원해 분석한다. 배포된 작은 기록의 `navigation_closeout.json`은 원본 요약에서 필요한 종료 정보를 추린 자료이며, 큰 원본은 압축본에 남아 있을 수 있다.

디스크를 정리할 때는 결과와 실패 기록을 먼저 지우지 않는다. 압축본의 전체 해시와 내부 파일의 해시를 검증한 뒤, 내용이 같은 큰 중복 파일만 정리하고 복원 경로를 기록한다. 원본이 사라져도 분석 가능하다는 판단에는 실제 보존 검증이 필요하다.

## 13.8.8. 실습 보고서와 다음 단계

실습 보고서는 성공 여부 한 줄 대신 다음 내용을 포함한다.

1. **실행 조건:** 기본 모드 여부, Level, 사례 UUID, 소스·설정 식별 정보.
2. **완료한 동작:** 요청·완료 단계와 실제 이동·관측 근거.
3. **종료 결과:** 정착, worker·goal·자식 프로세스 회수, bag 종료, 잔여 검사.
4. **실패 판독:** 실패했다면 최초 원인과 발생 시점, 뒤따른 오류와의 구분.
5. **검증의 한계:** 한 번의 실행으로 확인한 사실과 아직 확인하지 못한 기능.

이 절의 기본 수행 과제는 Level 2와 Level 3에서 이동·관측·종료 기록을 읽는 것이다. 실행 중 실패했다면 완료한 범위와 정지·회수 과정을 근거로 설명한다. 확장 과제에서는 과거 Level 2 사례의 BT SUCCESS와 최종 FAIL이 함께 존재한 이유를 설명한다. 두 과제를 전체 연속 임무 성공률로 합산하지 않는다.

향후 과제는 최신 버전의 연속 파지·귀환·내려놓기 재현성과 Level 3의 충돌 없는 파지 이후 동작이다. 기본 실습의 완료가 이 과제를 검증한 것은 아니다. 기능이 성립한 뒤에 소스와 조건을 고정하고 반복 평가를 해야 하며, 종료 기한이나 접촉·관측 조건을 임의로 바꿔 실패를 숨겨서는 안 된다.

별도의 교육용 확장 평가에는 성공률 80% 이상, 정상 완료 임무 평균 600 sim초 이하, 최종 위치 오차 10cm 미만 등의 완화 정책이 마련되어 있다. 그러나 이는 이번 기본 실습의 PASS 조건이나 이미 달성한 반복 평가 결과가 아니다. 적용 대상과 측정 집합은 [교육용 평가 정책](SECTION_13_8_EDUCATION_CRITERIA_SPEC_20261112_KO.md)에서 확인한다.

이 절에서 확보하는 것은 실행한 동작, 멈춘 이유, 종료 근거를 설명하는 능력이다. 이후 모델 최적화와 배포를 다룰 때에도 이 구분을 유지해야 한다. 처리 속도가 빨라졌다는 결과와 로봇 임무의 기능·안전 검증은 각각의 증거로 확인한다.
