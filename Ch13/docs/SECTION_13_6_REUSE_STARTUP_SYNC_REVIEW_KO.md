# 13.6 시작 동기화 원인 조사와 제한 수정

작성일: 2026-11-03. 기존 v1~v4 감사와 실패 증거는 보존한다. 이 문서는 후속 조사이며 기존 실패를 PASS로 바꾸지 않는다.

## 자연 재현으로 확인한 원인

진단 v5는 gate 동작과 기한을 유지하면서 native 수신 시각, Python 처리 시각, 원본 stamp, clock의 수신 시각, 최초 fault의 pending 항목을 기록했다. 기록은 메모리에 제한해 유지하고 종료할 때 저장했다. 시작 전용 실행은 동작 허가·목표 전송·팔 명령 없이 DISARMED 상태만 관찰한다.

- `9b72a34e-a1f2-4dfa-a2c6-e18f446e24b8`: 시작 PASS, 정상 회수.
- `6cde23d3-508a-4cbd-bb4b-e32d1126db07`: 시작 FAIL 자연 재현, 동작 허가 없음, 정상 회수.
- 예정했던 세 번째 진단은 두 번째 실패에서 순차 실행이 중단되어 실행하지 않았다.

두 번째 실행의 navigation trace에서 확인한 순서는 다음과 같다. wall 값은 동일 boot 안의 CLOCK_MONOTONIC 초다.

| 사건 | simulation stamp(ns) | native 수신(wall s) | Python 처리(wall s) |
|---|---:|---:|---:|
| 이전 clock | 68,000,000 | 56.555098588 | — |
| scan | 162,000,000 | 56.724943588 | 56.899189788 |
| scan pending 등록 | 162,000,000 | 원본 유지 | 56.899195388 |
| 따라잡은 clock | 180,000,000 | 56.748077088 | 56.899591988 |
| pending 만료 판정 | 162,000,000 | 원본 유지 | 56.899595188 |

clock은 scan 수신 뒤 **23.1335ms**에 native 수신돼 50ms 이내에 따라잡았다. 판정 시 scan의 원본 수명도 **174.6516ms**로 300ms 이내였다. 하지만 기존 `FutureInbox.ready`는 clock이 이미 따라잡았는지 확인하기 전에 Python 처리 시점까지의 경과가 50ms를 넘었다고 거절했다. 이 자연 재현 사례는 시작 단계의 처리 지연을 clock 수신 지연으로 오인한 오탐이다.

이 증거로 과거 모든 FUTURE_SOURCE 실패의 원인을 확정할 수는 없다. 이전 v4 실패에는 같은 수준의 trace가 없다. navigation 처리 자체가 약 150ms 지연된 이유도 아직 확정하지 않았다. 같은 실행의 gateway는 clock을 신속히 처리했으므로, 이 사례를 전체 DDS clock 전송 지연으로 설명하지 않는다.

## 수정 계약

동작 허가 이전이고 clock이 이미 원본 stamp를 따라잡았을 때만, native clock 수신 시각과 원본 입력 수신 시각의 차이로 50ms 기한을 검사한다. 원본 입력과 clock의 수신 수명은 각각 300ms 이내여야 한다. 비유한 값과 미래 수신 시각은 거절한다.

clock이 아직 따라잡지 않았거나 동작 허가 이후라면 기존 처리 시각 기준 50ms 거절을 유지한다. gateway의 100 simulation ms 즉시 거절 조건, 원본 stamp·수신 시각·소유자 검사, 관측 300ms 및 과거 TF 100ms 계약은 바꾸지 않았다. pending 항목이 남으면 arm/enable을 거절하며 성공적인 명시적 허가 후 시작 모드를 종료한다. idle이나 작업 인계로 시작 모드를 재활성화하지 않는다.

## 검증 기록

자연 재현의 정확한 시각을 회귀 시험으로 고정했다. 해당 경로 수용, 실제 clock 지연 거절, 오래된 관측 거절, 비정상 clock 수신 시각 거절, 미확인 clock·동작 중 기존 기한 유지, pending 중 동작 허가 거절을 포함한다. 새 시험의 RED 확인 뒤 최소 수정과 기존 계약 시험을 함께 실행해 15개가 통과했다.

수정 v6의 첫 시작 전용 실행 `26db0475-6e6c-49a4-9dfa-f6529114d052`는 PASS, 동작 허가 없음, 정상 회수였다.

수정 v7은 같은 시작 제어 로직에 아래 카메라 시험 준비 확인 및 수정 파일의 LF 정규화를 적용한 별도 동결이다. 소스 239파일·원본 자산 94파일, manifest SHA256은 `2baf5b99086cbd858815517a9c47c89f18c94f0fa7199475372c9fe77ee5040f`이다. v5/v6 동결은 그대로 보존했다.

| v7 확인 | 결과 |
|---|---|
| 전체 navigation + manipulation 시험 | 179 PASS, 77.06s |
| 별도 13.6 build | 6개 패키지 완료, 16.5s |
| 시작 전용 `ed25c88a-d55d-4e6d-ad20-d0da018464de` | PASS, 동작 허가 없음, 정상 회수 |
| 시작 전용 `ef08c35c-091c-46b5-a8b2-923285369c74` | PASS, 동작 허가 없음, 정상 회수 |
| 팔 취소 `c70aeb1c-8422-43d0-b28a-986fbb19a027` | 실행·독립 판정 PASS, 실제 CANCELED, 정상 종료 11개 |
| 13.5 free `01895ab8-a68a-46d1-b2e7-bbe5b24c17e2` | 실행·독립 판정 PASS, 실제 이동 0.623541m 및 기존 edu_stop_v2 통과 |
| 13.5 cancel `3c16da2b-f247-4fd4-ae5b-e90863e5181a` | 실행·독립 판정 PASS, 실제 이동 0.306450m 후 취소·기존 정착 기준 통과 |
| 최종 소유 프로세스·엔진 잠금 | 잔여 없음, lock free, PASS |

위 실제 회귀는 v7을 `CH13_REUSE_FREEZE`로 명시해 실행했다. 기존 `run_case.sh` 기본 동결은 아직 v4이며 현재 수정 소스와 일치하지 않는다. 최종 배포판의 기본 동결 교체와 전체 인수는 M5에서 별도로 처리한다. v7을 v4와 해시가 같다고 설명하거나, 수정 후 수행하지 않은 전체 picking matrix를 수행했다고 주장하지 않는다.

원본 증거는 로컬에 그대로 유지하고 각 사례의 `raw.tar.gz`/`raw_manifest.json`을 게시 대상으로 만든다. 모델·가중치는 포함하지 않는다. 전체 시험의 성공·실패 로그, build/freeze 기록과 최종 잔여 검사는 `Ch13/evidence/section_13_6_reuse/startup_sync_validation_20261103/`에 별도로 보존한다.

## 재개 후 추가로 드러난 시험 준비 문제

전체 회귀 첫 재확인은 178 PASS / 1 FAIL(87.24s)이었다. 실패는 기존 카메라 분리 시험의 renderer warmup 15초 초과였으며, 시작 동기화 7개 시험은 통과했다. 잔여 검사도 PASS였다. 카메라만 단독 재확인하자 warmup은 통과했으나, 450ms 관찰 구간에서 DDS 수신 0건으로 실패했다(1 PASS / 1 FAIL, 23.78s).

DDS publisher 발견을 먼저 확인하는 별도 진단에서는 4개의 실제 capture와 4개의 수신, 원본 capture journal 및 정상 종료를 확인했다(2 PASS, 7.45s). 기존 시험은 volatile publisher의 첫 전송을 DDS 발견과 경쟁시켰다. 시험에만 최대 5초의 publisher 발견 확인을 추가했다. 기존 차단 시간, 전송 구간과 영상 개수 기준, 실제 camera runtime은 바꾸지 않았다. 최초 warmup 초과의 원인은 이 진단으로 확정되지 않았으므로 별도 실패로 보존한다.

그 후 전체 회귀는 다시 178 PASS / 1 FAIL(89.29s)이었다. 이번에는 카메라 시험은 통과했으며, 기존 `test_engine_clock_pause_latches`가 clock 중단 주입 **이전** fresh 입력 준비 3초 조건에서 실패했다. 따라서 clock 중단 검출 자체의 실패로 분류하지 않는다. 소스나 기한을 바꾸지 않은 단독 재확인은 1 PASS(3.21s), 전체 회귀는 179 PASS(77.06s)였다. 준비 단계 실패의 원인은 미확정이다. 이러한 준비 단계 실패를 숨기거나 통과한 재시도만으로 반복 강건성을 주장하지 않는다.

## 판정과 남은 범위

자연 재현한 한 시작 오탐 분기는 원인 추적·실패 회귀 시험·제한 수정·실제 회귀까지 완료했다. 제어기와 관측 수명을 느슨하게 하지 않고 수정했다. 수정 부분은 단일 작업자가 별도 diff 검토를 했으며, 독립 검토자의 검토를 대체하지 않는다.

반면 모든 과거 시작 실패의 동일 원인 여부, Python 처리 지연의 근원, 렌더러 warmup 및 기존 DDS 시험 준비 실패의 반복성은 미확정이다. 전체 13.6 최종 인수·가이드 확정·배포판 전환은 완료하지 않았다. 이 한정된 수정 검증을 전체 플랫폼의 시작 안정성 보증으로 확대하지 않는다.

이 단계는 시작 오류의 특정 분기 수정 검증이다. 전체 13.6 인수·게시 완료 또는 반복 강건성 보증을 뜻하지 않는다.
