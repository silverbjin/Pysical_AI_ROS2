# 렌더러·DDS 시작 준비 결함 수정

작성일: 2026-11-03. 이전 시작 동기화 조사와 v1~v4 실패는 그대로 보존한다. 이 문서는 후속 시작 준비 조사다.

## 확인한 결함과 수정

### 1. 실패한 초기화가 성공 준비 이벤트를 발행

기존 `render_process`는 정상 첫 렌더 뒤에도, 예외 처리의 `finally`에서도 같은 `ready` 이벤트를 설정했다. 부모는 비동기 frame receiver가 오류를 옮기기 전에 이 이벤트와 아직 살아 있는 자식만 확인하면 `CameraWorker`를 반환할 수 있었다.

실제 MuJoCo 모델에서 `reuse_rgbd` 카메라를 누락시키고 receiver 처리를 400ms 지연시키자, 초기화가 실패했는데도 생성자가 정상 반환했다. 새 회귀 시험은 수정 전 `DID NOT RAISE`로 실패했다.

이를 전용 단방향 시작 응답 채널로 수정했다. 자식은 실제 첫 렌더가 끝났을 때만 READY를 응답한다. 초기화 예외는 별도 ERROR로 동기 전달한다. 부모는 frame receiver의 실행 순서에 의존하지 않는다. 입력·렌더 프레임·DDS 발행 경로는 유지했다.

### 2. 종료한 자식을 살아 있는 렌더러의 준비 시간 초과로 오인

준비 이벤트를 발행하기 전에 자식이 종료하면, 기존 부모는 15초를 기다리고 일반적인 warmup deadline으로 보고했다. 실제 자식 종료 코드 7을 주입한 회귀 시험에서 이 오분류를 확인했다.

이제 시작 응답 채널의 EOF를 구분해 자식 종료와 종료 코드를 보고한다. 살아 있으나 준비가 끝나지 않은 경우에만 기존 15초 기한을 적용하며 마지막 진행 단계도 표시한다. 오류 시 원래 close/join 경로를 수행한다. 주입한 비정상 종료를 정상 회수 성공으로 세지 않는다.

### 3. DDS 발행자 발견만으로 영상 전달 준비를 판단한 시험

이전 진단에서는 graph에서 writer를 발견한 뒤에도 실제 네 장의 capture·publish와 영상 수신 0건이 기록됐다. writer 발견은 첫 영상 전달 완료와 같지 않다.

카메라 분리 시험은 기존 5초 준비 기한 안에서 실제 bootstrap 영상의 수신까지 확인한 뒤 측정을 시작하도록 바꿨다. bootstrap과 측정 stamp를 구분해 준비 영상이 측정 성공 수에 섞이지 않는다. 측정 동안 부모 보관 callback은 finally에서 명시 해제할 때까지 차단한다. 기존 2초 callback 진입 기한과 3개 프레임의 450ms 측정 구간은 유지했다. 최신 슬롯의 offer가 일시 거절될 수 있어 callback 진입까지 기존 2초 안에서 offer를 재시도한다. 실제 엔진의 명령이나 관측을 재발행·재시각화하는 동작은 없다.

### 4. 오류 traceback이 실패한 생성자의 공유 자원을 보유

초기 수정의 전체 시험은 181개가 통과했으나 ResourceTracker 재진입 경고 17건이 발생했다. 이를 정상으로 넘기지 않았다. 실제 자식 종료를 주입하고 오류 traceback을 보존한 뒤 `/dev/shm/sem.mp-*`의 전후 차이를 검사하자 새 공유 semaphore가 남았다(RED, 3.77s).

오류 traceback은 실패한 생성자의 `self`를 보존한다. 기존 close/join만으로는 그 객체가 가진 Queue·Event·Value 참조까지 해제되지 않았다. 실패한 생성자에서 자식과 수신 스레드의 종료를 확인한 뒤 process handle을 닫고 해당 참조를 즉시 해제하도록 했다. 이후 자원 검사를 포함한 시작·실패·카메라 분리 시험 5개가 통과했다(17.28s). 수동 semaphore 삭제, GC 비활성화·정책 변경, ResourceTracker 경고 숨김은 하지 않았다.

## 단계별 기록과 유지한 계약

- 부모 spawn 시작·완료·결과 수신, 자식 target 진입, ROS import/init, Node와 publisher 생성, Renderer 생성, 첫 렌더, READY/ERROR 시각을 기록한다.
- `renderer_captures.json`을 사용하는 실행은 부모의 `renderer_startup.json`도 남긴다. 실제 초기화 실패 때도 원본 오류와 진행 단계가 저장되는지 실패 시험을 먼저 실행했다.
- 기존 DDS fixture의 fresh 입력 준비 3초는 유지했다. 실패 시 clock/graph 원본 시각, 실제 sample, owner 수, relay 종료 코드, executor 생존 여부를 함께 표시하도록 했다.
- 렌더러 시작 제한 15초, 관측 300ms, 과거 TF 100ms, 동작 중 clock 50ms와 fault latch·명시 재활성화 계약을 변경하지 않았다.
- 다리 정책·native PD·질량·마찰·힘 cap·캡처 stamp·최초 receipt·실제 DDS GID를 변경하지 않았다.

## 검증

두 시작 결함의 회귀 시험은 수정 전 2 FAIL(18.22s), 수정 후 기존 실제 카메라 분리 시험과 함께 4 PASS(12.65s)였다. 별도 완결된 관측 진단에서 실제 카메라 시작 6회와 DDS fixture 12회가 모두 통과했다. 이 횟수는 강건성 통계가 아니다. 관측 도구 개발 중 발생한 pytest 경로·Node 타입·legacy 계측 오류는 제품 실패 통계에서 제외하고 원본을 보존했다.

전체 회귀는 단계 기록 파일 저장을 추가하기 전에 181 PASS(99.75s)였다. 기록 파일 저장은 실제 초기화 실패 후 파일이 없다는 RED를 확인한 다음 구현했다.

중간 v8은 181 PASS / 경고 17건(104.18s), 6개 패키지 build 16.0s였다. 소스 240개·원본 자산 94개, freeze SHA256 `b22ee70154852f5d764961015b44906e80e9b3122ac0209f5d740bb25877372a`이다. v8의 실제 시작 전용 `ffb681a0-418c-4db2-aa30-f394becbb248` 및 `cae95d59-79de-4ea1-a1c0-787c631b5652`는 PASS, 동작 허가 없음, 정상 회수였다. v8 free `3d2a3b14-04bf-47e0-b977-679e071ef9b0`와 cancel `8bca8358-a147-447b-8630-f6dce2a9c067`는 실행 exit 0이었다. 경고 수정 뒤 결과는 v9로 따로 동결하며 v8을 소급해서 경고 없는 성공으로 기록하지 않는다.

최종 v9는 전체 182 PASS(118.45s), pytest 경고 0건, 6개 패키지 build 완료(17.1s)다. 소스 240개·원본 자산 94개, freeze SHA256은 `53ecf6fa5e7e6c41b16ff9f7445f50a05a504dcdfcbb6c6ba8ff887fbbddd2b7`이다. 실패 경로의 자원 해제 외 정상 렌더·DDS 경로는 v8과 같다.

| v9 cancel `0b8e87c8-1c23-43a6-908d-8ac234d37d55` | 실행·독립 판정 PASS, 실제 0.314818m 이동 후 취소·기존 정착 기준 통과 |
| 최종 잔여·동결 검사 | 소유 stack 잔여 없음, lock free, 소스·94자산 해시 PASS |

사례별 판정은 `Ch13/evidence/section_13_6_reuse/preparation_fix_validation_20261103/CASE_INDEX.json`에 있다. 진단 도구 자체의 실패를 포함한 원본 로그, RED/GREEN, 중간 경고, 최종 시험·build·freeze·잔여 검사를 같은 폴더에 보존했다. 실제 실행 6건은 모델·가중치를 제외한 `raw.tar.gz`/`raw_manifest.json`으로 제공하며 원본을 삭제하지 않았다. 압축본의 각 파일을 원본 해시와 대조했다.

실제 회귀에는 각 revision을 `CH13_REUSE_FREEZE`로 명시했다. 기존 runner 기본값은 아직 v4이며 현재 수정 소스와 일치하지 않는다. 기본값을 포함한 최종 실습 배포 전환은 이번 제한 수정 검증과 구분한다. 검토는 사용자 지시에 따라 단일 작업자가 별도 diff 검토로 수행했으며 독립 검토자의 검토보다 약하다.

## 해석의 한계

과거의 renderer 15초 초과가 정확히 어느 내부 단계에서 발생했는지는 당시 기록만으로 확정할 수 없다. 과거 DDS fixture의 fresh 준비 3초 초과도 이번 완결된 단계 진단에서는 자연 재현되지 않았다. 이를 모두 위 두 코드 결함 때문이라고 단정하지 않는다.

확인된 잘못된 준비 성공·종료 오분류·시험의 DDS 준비 경쟁을 제거했고, 재발 시 원인을 구별할 기록을 남겼다. 실제로 준비 기한을 넘기면 계속 실패로 거절한다. 최종 13.6 picking 전체 인수·기본 실행 동결 교체·실습 가이드 확정은 별도의 M5 작업이다.
