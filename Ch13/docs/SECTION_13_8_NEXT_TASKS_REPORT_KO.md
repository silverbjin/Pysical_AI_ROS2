## 4. T1: 반복되는 지연·시작 순서

### 4.1 원본 관측 만료

v20의 큰 pre-offer/capture 단계 지연을 source capture→request offer→render 시작/종료→발행→최초 native 수신→검증→engine 적용 순서로 연결한다. 현재 SensorSuite의 최근256개 통계와 전체 기록 범위를 구분한다. Python queue의 put 반환을 전달 완료로 보지 않는다.

설치 버전의 CPython Queue/ROS executor·relay 구현을 우선 다시 확인하고,저장 상태의 작은 probe→필요한 실제 부하 순으로 재현한다. 원인이 producer 작업인지,queue/CPU 경합인지,수신/검증 적체인지 확인한 뒤 한 경계만 수정한다. 재현되지 않으면 미확인으로 기록하고 새로운 임계값을 추측하지 않는다.

### 4.2 heartbeat producer 공백

v21의364.214ms 공백은발행이 멈춘 사건이다. 현재 원문 journal+owner GC 계측을 유지하고 필요하면 owner의 동기 준비/계획·직렬화/종료 I/O 구간을 제한된 계측으로 추가 분리한다. v22 최대235.980ms와GC63~65ms는 서로 겹치지 않았으므로GC만 원인으로 단정하지 않는다.

진단 결과가 같은 구조의 반복 실패를 가리키면 준비·계산·기록과 live owner polling의 경계를 재검토한다. 독립 heartbeat thread로 stale snapshot을 새 권한처럼 발행하지 않는다. 수정 후 원래 공백/예외 회수 재현과 영향을 받는 회귀를 확인한다.

### 4.3 실제 cold-start 미래 입력 실패

v24 시작 실패는 base/clock의 원본 native receipt/GID·FutureInbox pending/clock catch-up을 대조한다. 합성 시험의 DDS 매칭 대기를 고쳤다고 production startup도 해결됐다고 생각하지 않는다. 현재 startup trace를 먼저 사용하고 공식 rclpy 매칭 수/실행 순서 및 실제 ingress 경계를 비교한다.

새 준비 gate가 필요하면 DISARMED/최초 motion 허가 이전의 준비일 뿐임을 명시한다. 기존 미래 입력 거부·50ms 순서 경계·300ms 수명·명시적 arm/FAULT latch를 유지한다. 같은 설정을 성공할 때까지 반복해 실패를 버리지 않는다.

완료 조건은 '여러 fault 문자열이 사라짐'이 아니라,원인별 증거·최소 수정·원래 음성 조건 거부·정상 회수와 남은 한계의 기록이다. 형식적인 소수 회 통과를 모든 부하의 실시간 보장으로 확대하지 않는다.

1. 원고의 '놓침/낙하 실패'와 현재 world 높이 기준이 평가하려는 물리 현상을 구분한다. 경사면의 기준 좌표계,몸통/손끝 운동과 물체 slip을 명시한다.

3. 새 평가 정의가 필요하면 현재 정의와 별도 버전·출력명을 갖고,낙하·한쪽 접촉 상실·상대 slip·지지면 충돌·가짜 시간/누락 자료의 음성 시험을 먼저 정한다.

## 7. T4~T6: 공통 테이블과 난이도 월드

### 공통 테이블

원고의 `(3,1)` 테이블은 바닥 Level1과 별도 scenario다. 높이·물체/수령 지점·카메라·접근 방향·지원 형상을 동결한다. 초기 고정 시야 밖일 경우 카메라 health와 물체 부재를 구분하고,알려진 지도 기반의 소유된 이동 뒤 실제 fresh 3D를 획득한다. 정답 object 좌표를 제어용 관측으로 대신 넣지 않는다.

먼저 정적 시야/6D IK·충돌 부품을 확인한 뒤 같은 engine의 필수 연속 동작을 검증한다. 일반 물체 인식이나 새 학습을 기본 범위에 추가하지 않는다.

### Level2: 박스와5도 경사

장애물 치수/위치·경사 방향/길이·승강 경계·대상 위치를 scenario metadata로 공개한다. 원본 모델/정책을 유지한 실제 기하와 Nav2 지도/costmap을 일치시킨다. 공식 Nav2 footprint·collision checking 패턴은 실제 로봇·팔·적재물 외형과 함께 검토한다.

작은 부품에서 geometry/경사각/충돌·지도 투영을 확인하고 가장 불확실한 필수 이동/운반부터 순차 검증한다. 단순 계획 경로 존재를 실제 경사 통과 성공으로 쓰지 않는다.

### Level3: 문과테이블 아래 대상

문 폭과 팔/적재물을 포함한 실제 전체 외형을 확인한다. 테이블 상판·다리의3D 충돌과2D 지도를 구분하며 상판을 무조건 전체 높이 장애물로 투영하거나 없애 통과시키지 않는다. 테이블 아래 물체의 가림·접근 방향·팔 도달성을 작은 시험으로 먼저 확인한다.

현재 원본 정책/기구학 범위에서 불가능한 과제는 실패와 원인을 공개한다. torso 고정/teleport/물리 weld/새 WBC로 실습 범위를 몰래 확대하지 않는다.

## 9. T8: 교재 패키지·복원·자체 검토

원격 브랜치/commit 다운로드→외부 자산 취득→의존성→분리 build→실제 child/설치 감사→터미널별 환경→원고 소절별 명령→예상 결과·실패·정상 종료 판독을 연결한다. 원고의 교육용 코드와 실제 설치 API/알려진 원통/ground-truth localization profile 차이를 표시한다.

학생 기본 실습과 개발자의 부품/고장 주입/회귀를 구분한다. 학생에게 과거 전체 suite와 모든 장시간 matrix를 매번 요구하지 않는다. bag/replay의 실제 지원 범위도 명시한다.

빈 폴더에서 archive/개별 파일 hash 복원을 확인하고 외부 자산 제외·실행 동결·설치 데이터 누락을 점검한다. clone+새 engine 검증은 실제 수행한 경우에만 완료라고 쓴다. 사용자의 단일 작업자 지시에 따라 자체 검토의 독립성 한계를 남긴다.

최종 완료 자료에는 원고 항목별 실제/모의/미지원,성공/목표 미달/미확인,전체10회 분모,실행·회수 증거,공식 ref,재현 한계를 포함한다. 이번의 원격 게시 지시는 현재 브랜치 게시이며 앞으로의 main 병합·PR 생성으로 자동 확대하지 않는다.

## 10. 실행 원칙

공식 문서·GitHub의 **실제 설치 버전** 구현/시험을 먼저 조사하고 채택 패턴·차이를 짧게 기록한다. 구현 계획 실행은 `superpowers:executing-plans`로 단일 작업자가 진행한다. 저장 자료→작은 부품→필요한 실제 사례 순서를 지키며,같은 실패 계열이 두 최소 수정 뒤에도 남으면 의존성/구조/실행 경계를 재검토한다.

engine 중 build/pytest/대용량 분석을 병행하지 않는다. 새 변경은 새 source freeze/UUID로 분리하며 기존 v7/v24·과거 FAIL을 수정해 성공으로 만들지 않는다. `sources/`,Ch01~12·외부 checkout/underlay 원본은 읽기 전용으로 유지한다. 사용자 원본·untracked 자료를 임의 stage/정리하지 않는다. OS/드라이버/전역 시간·우선순위를 변경하지 않는다.
