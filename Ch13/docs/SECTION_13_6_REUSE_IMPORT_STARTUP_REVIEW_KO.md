# 최종 인수 전 시험 자식 시작 지연 조사

작성일: 2026-11-03. 이전 준비 결함 수정과 별개로, M5의 전체 회귀에서 다시 발생한 시작 제한 초과를 조사했다. 과거 실패를 삭제하거나 PASS로 바꾸지 않는다.

## 마지막 단계 이름과 전체 지연 원인의 구분

최초 사전 시험은 189 PASS / 2 FAIL(125.97s), 일반 실행 경로 재확인은 190 PASS / 1 FAIL(120.82s)이었다. 실패한 카메라의 마지막 단계는 `node_begin`이었다. 처음에는 Node 생성 자체의 장기 정체로 해석했으나, 영구 경로에 보존한 전체 시각을 비교한 결과 이를 바로잡았다.

| 실패 사례의 구간 | wall 초 |
|---|---:|
| 부모 spawn 완료 → 자식 target 진입 | 8.8946 |
| ROS import | 4.3611 |
| ROS init | 0.0062 |
| Node 생성 진입 후 남은 준비 예산 | 약 1.74 |
| 전체 부모 준비 기한 | 15.00 |

즉 Node 생성이 15초 멈췄다는 증거가 아니다. 자식의 bootstrap·import가 대부분의 예산을 사용했다. 별도 스택 관측 실행에서는 191개가 통과했지만 시작에 14.79초가 걸린 사례가 있어, 이를 충분한 개선이라고 해석하지 않았다.

초기 시험의 `/tmp` 기록은 다음 WSL boot에서 사라져 보존하지 못했다. 이후 진단은 새 고유 작업 경로를 pytest basetemp로 사용했고, 이전 경로를 재사용·삭제하지 않았다. 원본 실패 stdout과 이후 영구 기록을 모두 보존했다.

## 원인과 최소 수정

기존 여러 시험 파일과 conftest가 같은 source 경로를 각각 `sys.path` 선두에 추가했다. 전체 수집 뒤 경로는 60개였으나 고유 경로는 23개였다. Windows NTFS의 같은 디렉터리를 모듈 검색 때 반복 조회했고, 이 목록이 spawn 자식에게 그대로 전달됐다.

실제 `PathFinder`로 존재하지 않는 고유 이름을 20회 조회한 단일 관측에서 원본 목록은 3.0996754초, 중복 제거 목록은 0.5403957초였다. 이 측정은 캐시·호스트 조건을 포함한 한 번의 비교이며 일반적인 속도 보증이나 반복 통계가 아니다.

`run_tests.py`에서 수집 후와 각 시험 준비 시 경로의 첫 번째 항목을 보존하며 중복만 제거하도록 했다. source와 installed 패키지의 검색 우선순위 및 모든 고유 경로를 유지한다. 상대 경로 동등성·최초 소스 우선순위를 시험으로 고정했고 구현 전 2 RED를 확인했다. 엔진 코드·RMW·domain·ROS 시작 기한·관측 수명·GC 정책은 바꾸지 않았다.

UDP domain/ephemeral 범위도 조사했으나 실제 bind 충돌 원인은 확인하지 못해 설정을 바꾸지 않았다. [ROS 2 Jazzy의 domain 지침 원문](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Domain-ID.rst)은 참고 자료이며 이번 import 지연의 원인 증거로 사용하지 않는다.

## 검증과 v10 사전 동결

- 수정 뒤 일반 실행 경로의 전체 **193 PASS, 62.16s**, pytest 경고 없음.
- 시험 수집 경로 **60 → 23**, 최초 검색 순서 보존.
- 앞서 실패한 같은 카메라 fixture는 준비 **3.36s**, bootstrap **1.74s**로 READY.
- 별도 build **6개 패키지, 18.2s** 완료.
- v10 소스 **244개**, 원본 자산 **94개**, freeze SHA256 `803723f22d196f924552b8aa619b6d87060d7bf13a9a6fa60b4e4327ccfe5443`.

이 결과는 시험 검색 경로가 불필요하게 누적된 비용을 제거한 증거다. 모든 과거 실환경 시간 초과의 원인이 동일했다거나 WSL에서 하드 실시간 시작을 보장한다는 뜻은 아니다. 최종 16개 시나리오 인수 결과는 별도 최종 보고서에 기록한다.

## v11 시작 대기열 후속 수정

v10 첫 인수 배치의 pick은 팔 명령 전 future-clock 오류로 실패해 배치를 중단했다. 다른 추적 pick의 성공을 그 실패 대신 세지 않았다. 별도 회귀 시험에서 native clock은 원본 입력 뒤23.1ms에 수신됐지만 Python 대기열의 타이머가 clock 콜백보다 먼저 실행되는 유효한 순서를 재현하자 v10이50ms 오류로 거절했다(RED).

v11은 이 경우 동작 허가를 계속 차단하고 원본 입력의300ms 수명 안에서 실제 clock 수신 증거를 기다린다. clock을 처리한 뒤 원래 native 수신 차50ms와 clock 수명300ms를 검사한다. 실제로 늦게 수신된 clock, 만료된 입력, 동작 중50ms 초과는 계속 거절한다. source stamp나 receipt를 새 값으로 바꾸지 않는다. v10의 최초 pick은 trace가 없으므로 같은 원인이라고 소급 단정하지 않는다.

이후 전체194 PASS(62.54s), 6개 패키지 build19.0s, v11 source244/asset94의 별도 동결 뒤16개 인수를 수행한다. 현재 최종 기준과 사례는 [최종 인수 보고서](SECTION_13_6_REUSE_REPORT_KO.md)를 따른다. 이 문서의 v10 측정값과 실패는 그대로 보존한다.
